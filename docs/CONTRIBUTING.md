# 🤝 Contributing Guide (팀 협업 가이드)

이 문서는 우리 팀이 원활하게 협업하고 과제 요구사항을 준수하기 위해 정의한 협업 규칙입니다. 모든 팀원은 아래 규칙을 따라 작업을 진행합니다.

---

## 1. 🌿 브랜치 전략 (GitHub Flow)

우리 팀은 **GitHub Flow** 전략을 사용합니다. (`develop` 브랜치 없이 `main`과 `feature/*`만 운용)
- `main` : 항상 배포 가능한 상태 (팀 기준에서 코드가 깨지지 않는 안정 상태)
- `feature/*` : 모든 기능 추가, 문서 작성, 버그 수정 등을 수행하는 작업 단위 브랜치

### 우리 팀이 GitHub Flow를 선택한 이유 (3줄 요약)
1. 3~5인 소규모 단기 프로젝트 특성상 복잡한 Git Flow보다 단순하고 직관적인 브랜치 구조가 적합합니다.
2. 모든 변경 사항을 `feature/*`에서 `main`으로 향하는 PR 단위로 관리하여 빠른 코드 리뷰와 병합이 가능합니다.
3. 브랜치 관리 비용을 줄이고 이슈 추적, 코드 리뷰, 의도적 충돌 해결 실습에 집중할 수 있습니다.

---

## 2. 🏷️ 브랜치 네이밍 규칙

브랜치는 `feature/<작성자이름>-<작업주제>` 또는 `feature/#이슈번호-<작업주제>` 형식으로 명명하며, 영문 소문자와 하이픈(`-`)을 사용합니다.

### 브랜치 네이밍 예시
```bash
feature/lee-contributing
feature/kim-math-utils
feature/park-conflict-test
```

---

## 3. 📝 커밋 메시지 컨벤션

커밋 메시지는 `<Type>: <Subject>` 형식을 따르며, 무엇을 왜 바꿨는지 명확히 드러나야 합니다.

### 커밋 Type
- `feat`: 새로운 기능(유틸 함수 등) 추가
- `fix`: 버그 및 오류 수정
- `docs`: 문서 추가 및 수정 (`README.md`, `docs/*`, `team/*` 등)
- `refactor`: 기능 변경 없는 코드 구조 개선
- `chore`: 폴더 구조 세팅, 설정 파일 수정 등

### 작성 예시
```text
feat: 문자열 뒤집기 유틸 함수(reverse_string) 추가
docs: CONTRIBUTING.md 내 코드 리뷰 규칙 섹션 작성
fix: 0으로 나눌 때 발생하는 ZeroDivisionError 예외 처리 추가
```

### 🚫 의미 없는 커밋 메시지 금지 (판정 기준)
다음과 같은 커밋 메시지는 절대 사용하지 않습니다.
1. **변경 대상을 유추할 수 없는 단어만 있는 경우:** `update`, `fix`, `temp`, `wip`, `final` 등
2. **무엇을/왜 바꿨는지 드러나지 않는 경우:** `bug fix`, `edit file`, `코드 수정` 등 구체적 대상과 효과가 없는 메시지

## 4. 🚀 PR (Pull Request) 작성 규칙

- 모든 작업은 **GitHub Issue를 먼저 생성**한 뒤, `feature/*` 브랜치에서 작업 후 `main` 브랜치로 PR을 보냅니다.
- `main` 브랜치에는 직접 Push할 수 없으며, **최소 1명 이상의 동료 Approve(승인)**가 있어야 병합(Merge)할 수 있습니다.
- 모든 팀원은 **최소 2개 이상의 PR을 생성 및 병합**해야 합니다.

### PR 본문 필수 포함 항목 (템플릿)
PR 생성 시 본문에 아래 내용을 반드시 포함합니다 (`Closes #이슈번호` 필수):

```markdown
## 연결 이슈
- Closes #<issue_number>

## 변경 사항 (What)
- 어떤 파일/코드를 추가하거나 수정했는지 구체적으로 작성

## 변경 이유 (Why)
- 이 작업이 왜 필요한지 배경 설명

## 테스트/검증 방법 (How)
- [ ] 로컬 실행 또는 간단 테스트 통과 여부 확인
- [ ] 충돌 가능성 체크 (필요시)
```

---

## 5. 👀 코드 리뷰 규칙 (최소 품질 기준)

코드 리뷰는 단순 확인이 아니라 코드 품질을 높이고 서로 배우는 과정입니다.

### 팀원별 필수 기준
- 각 팀원은 본인 PR을 제외하고 **최소 2개 이상의 PR에 코드 리뷰를 작성**해야 합니다.
- 본인 PR에서 받은 리뷰 코멘트를 **최소 1회 이상 실제로 반영**(추가 커밋, 코드 수정, 답글 논의)한 기록을 남겨야 합니다.

### 리뷰 최소 품질 기준
- **"LGTM", "좋아요", "확인했습니다"만 남기는 리뷰는 인정하지 않습니다.**
- 반드시 **특정 파일이나 코드 라인을 근거로 한 실질 코멘트 1개 이상**을 포함해야 합니다.
  - *예시 1 (질문):* "15번 라인에서 리스트 대신 튜플을 반환하도록 작성하신 특별한 이유가 있을까요?"
  - *예시 2 (리스크 지적/대안 제안):* "입력값이 빈 문자열일 때 에러가 발생할 수 있으니, 상단에 예외 처리를 추가하는 것은 어떨까요?"
- 리뷰어와 작성자 간 **최소 1회 이상의 상호작용(답글 또는 수정 커밋 반영)**이 PR 기록에 남아야 합니다.

## 6. ⚠️ 충돌(Conflict) 발생 시 기본 대응 흐름

팀 전체 기준으로 프로젝트 기간 중 **최소 2회 이상(비자명 충돌 1회 포함)** 의도적 충돌을 경험하고 해결 과정을 기록합니다.

### 1) 누가 해결하는가? (Who)
- 나중에 PR을 병합하려는 **PR 작성자**가 주도하여 해결하되, 충돌이 발생한 상대방 코드 작성자와 반드시 함께 논의하여 코드 손실을 방지합니다.

### 2) 어떻게 해결하는가? (How)
1. **상황 공유:** 충돌 발생 시 해당 코드 작성자에게 상황을 공유하고 어떤 코드를 살릴지(Keep both / Choose one / Refactor) 합의합니다.
2. **로컬 병합 및 수정:**
   ```bash
   git switch main
   git pull origin main
   git switch feature/<내-브랜치>
   git merge main
   ```
3. **충돌 마커 제거 및 검증:** 파일 내 `<<<<<<<`, `=======`, `>>>>>>>` 마커를 확인하여 합의된 코드로 수정한 뒤 정상 동작을 테스트합니다.
4. **커밋 및 푸시:**
   ```bash
   git add .
   git commit -m "fix: main 브랜치 병합 충돌 해결"
   git push origin feature/<내-브랜치>
   ```

### 3) 어디에 기록하는가? (Where)
- 충돌 상황, 충돌 마커 내용(`<<<<<<< HEAD` 등), 해결 전략 및 과정, 최종 결과와 배운 점을 **`docs/conflict-resolution.md`** 문서에 템플릿에 맞춰 상세히 기록합니다.
